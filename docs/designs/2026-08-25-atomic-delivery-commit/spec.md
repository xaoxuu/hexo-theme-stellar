# 功能与文档原子交付方案

## 1. 问题与目标

实现提交产生后才能取得 SHA，把该 SHA 手工登记回同一仓库会强制产生第二个文档提交。这个台账重复 Git 历史，也让文档与功能在时间上分离。

目标是把一个需求的实现、测试、知识库、公开文档、方案状态与验证记录组成一个交付提交。提交前必须基于最终功能 diff 完成文档语义核验；提交后的 SHA 只进入 GitHub issue 评论与发布输出。

成功标准：

- 当前规范与主题开发 Skill 在提交前阻断缺失或过时的文档。
- 功能和对应文档一次暂存、一次提交，不再产生 SHA 登记提交。
- `npm run check` 保留代码、Schema、性能与知识库硬事实检查，不再维护 Git 历史的副本。

## 2. 技术方案

- `AGENTS.md` 定义“文档同步核验”和“交付提交”，作为流程唯一权威；Codex 与 Claude Skill 保持相同的执行顺序与完成条件。
- 语义核验由 Agent 阅读最终 diff，逐项映射行为、配置、API、UI 与兼容性变化，检查说明、示例、字段名、默认值、边界和失败行为。现有 `verify.py` 继续验证可机械判断的硬事实，不声称替代语义核验。
- 删除 `VERIFICATION.md` 的短 SHA 表、`ci/check-release-docs.js` 及其单测；发版从 Git 历史汇总提交，从 CHANGELOG 读取摘要。

## 3. 影响范围

- 影响主仓库与主题仓库的 AI 协作规范、主题开发 Skill、项目总控 Skill、issue 交付约定、设计模板、发版说明与 `npm run check` 的内部组成。
- 不改变主题运行时、公开配置、npm 包内容或用户 API。
- 主工程仅修改协作规范、Skill 与本次规格，不修改现有内容、配置或项目里程碑状态；历史设计与已完成 checklist 的交付事实保持原样。

## 4. 验证方式

- 运行主题 `npm run check` 和知识库硬事实核查。
- 校验 Codex 与 Claude Skill 镜像一致并通过 Skill 格式验证。
- 搜索当前规范、Skill、发版指南与包脚本，确认不再引用活动的 SHA 登记流程。
- 运行 `git diff --check`；本次没有主题运行时代码或构建期 `scripts/` 改动，不执行主工程构建。
